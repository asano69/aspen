# DeepWiki Q&A with Code Context for Repository: maxnowack/signaldb
## Q1
signalDBのsolidアダプタがあるが、10万件規模のコレクションに対してreactive queryを張ると、購読コストや再計算コストが無視できない可能性がある
### Answer
ご指摘の通りです。`@signaldb/solid` のアダプタ `solidReactivityAdapter` は、購読単位ごとに `createSignal(undefined, { equals: false })` で依存を1つ作り、`notify()` で `rerun()` を呼ぶだけのシンプルな実装です。 signaldb:4-20  つまり通知が来るとクエリ全体が再実行されるため、セレクタが広い(例: `find({})`)場合は10万件規模では再計算コストが無視できません。

---

## コストの構造

- **購読コスト**: `Cursor.fetch()` などがリアクティブスコープ内(`isInScope` = `!!getOwner()`)で呼ばれると、クエリごとに `depend` が呼ばれ dependency が作られます。 signaldb:5-16  依存の粒度は「クエリ単位」なので、購読数自体はクエリ数に比例しますが、1通知あたりの再計算はクエリの結果セット全体に及びます。
- **再計算コスト**: `notify()` は `rerun()` でエフェクトを再実行させ、内部でクエリ再走査が起きます。`{ equals: false }` のため結果が同じでも必ず通知されます。 signaldb:6-13  テストでも変更後に `notify` が呼ばれクエリが再評価される挙動が確認されています。 signaldb:461-474 
- 大量書き込み時は `collection.batch()` が有効で、1万件の insert をまとめても `notify` は最後に1回だけ発火します。 signaldb:507-514 

## 緩和策(コードベース上の公式手段)

| 手段 | 効果 |
|---|---|
| `fieldTracking: true`(`.find()` オプション / `Collection.setFieldTracking`) | アクセスしたフィールド・items が変わった時だけ再実行。大規模データセット向けに明示的に最適化目的で導入されています。 signaldb:83-92 signaldb:113-125  |
| `fields`(projection) | 参照フィールドを絞り、関係ないフィールド変更での再実行を防ぐ。 signaldb:60-64  |
| `createIndex` / `indices` | 10万件のフルスキャンを避ける。テストでは `createIndex('num')` で非インデックス比10%未満の時間を要求しています。 signaldb:660-689  |
| `skip`/`limit` | 返す件数を絞りレンダリング・再計算量を削減。 signaldb:72-81  |
| `batch()` | 一括書き込み時の通知回数を1回に集約。 signaldb:477-515  |

実用上は、10万件のコレクションでは `find({})` のような無条件クエリを避け、セレクタ + インデックス + `fieldTracking` を組み合わせるのが SignalDB 側が想定する使い方です。 signaldb:127-131 


この回答は、先ほどの推測を裏付けるだけでなく、実装上の根拠まで示してくれていますね。整理すると、cardpodの設計判断は理にかなっていたと言えます。

## cardpodの選択の正当性

`queryCardsPage`/`countCards` は `{ sort: {...}, skip, limit, reactive: false }` を明示していますが、これは今回の回答が指摘する「10万件規模では `find({})` 系の広いセレクタは再計算コストが無視できない」というリスクを、そもそも**reactiveを使わないことで完全に回避**する選択です。

さらに、cardpodのアクセスパターンを見ると、reactive queryを使ってもあまり恩恵がなかったはずです：

- `queryCardsPage`: `skip`/`limit`はあるが `{}`（無条件セレクタ）→ 回答にある「セレクタ + インデックス + `fieldTracking`」の組み合わせ最適化の恩恵を受けにくい形
- ページング結果は `mergeCards` で毎回Solid storeに書き込まれるので、reactiveで自動追随させても、どのみち `windows[podId].ids` の並び替えや重複排除といった業務ロジックは手動でやる必要がある

つまり、reactive queryを使ったとしても `fieldTracking: true` や `createIndex` を別途チューニングする追加コストが発生するだけで、「明示的な関数呼び出し＋手動でSolid storeに反映」という今の設計より複雑になった可能性が高いです。simplicity重視の方針とも整合します。

## 一方で気に留めておくと良い点

`Collection.setFieldTracking` や `createIndex` は「後から有効化できる最適化」として存在するので、将来的にもし以下のような状況になったら検討の余地はあります：

- `queryCardsPage` のskip/limitクエリ自体が遅くなってきた場合（現状はIndexedDB上の話であり、SignalDB自身のインメモリ走査コストとは別軸の懸念点ですが）
- `position`/`pin` でのソートに `createIndex` を張ることで、フルスキャンを避けたい場合

ただし現状 `reactive: false` で運用している限り、`notify()`/`rerun()` 周りのコスト（今回の回答の本題）はそもそも発生していないので、**今すぐ手を入れる理由はありません**。「reactivityアダプタを使っていないなら `@signaldb/solid` 依存自体が本当に必要か」という以前の指摘は、この観点からもやはり見直す価値がありそうです（テストコード `cardsCollection.test.ts` だけのために依存しているなら、プレーンな `Collection` で書き換えて依存を削れる可能性があります）。

# SignalDBの懸念点 - Dexie.jsとの比較

## コードベースの記述量では明確にSignalDBが有利

これまで洗い出した通り：

| 観点 | SignalDB | Dexie.js |
|---|---|---|
| スキーマ宣言 | 不要（`new Collection<T>()`） | `.version().stores()` が必須 |
| 混在方向ソート（`pin:-1, position:-1, id:1`） | そのまま書ける | compound indexで表現不可。データモデル変更 or JS側ソートが必要 |
| pod単位の動的コレクション | `new Collection({name: ...})` で即座に | `new Dexie(...)`のライフサイクル管理（open/closeを明示） |
| テスト | persistenceなしで純インメモリテスト可 | `fake-indexeddb`導入が必要 |

これは事実として揺らぎません。`cardsCollection.ts` の実装量とテストの書きやすさは、SignalDBの方が明らかに軽量です。

## ただし「シンプルさ」の別側面：ランタイムの動作原理

SignalDBは基本的に**コレクション全体をメモリに保持し、`find()`のフィルタ・ソート・skip/limitはすべてJS側（mingo）で計算**します。一方Dexieは**IndexedDBのネイティブindex/カーソルを直接使って範囲検索**でき、該当するインデックスがあれば全件をメモリに載せずに済みます。

`CLAUDE.md` に「1ポットにつき10万件のノートまで」という要件がある以上、これは無視できない違いです：

- SignalDBの `queryCardsPage(podId, skip, limit)` は、内部的には10万件をメモリ上に持った状態で `sort` → `skip` → `limit` をJSで毎回計算している可能性が高い
- Dexieなら理想的には該当indexのカーソルを`skip`件分進めて`limit`件読むだけで済み、メモリ上に10万件を保持し続ける必要がない（ただし前述の通り、混在方向ソートを満たすindexを作れるかは別問題）

つまり「コードは書きやすいが、10万件規模でのメモリ使用量・クエリ実行コストは実測していない」という状態です。これは会話の中で検証していない部分なので、結論に含めるなら「保守性の観点では簡潔だが、大規模データでのメモリ効率は未検証」という留保をつけるべきです。

## 結論として言えること

- **「コードベースがシンプルになる」→ 妥当**（実装・テストの記述量という意味で）
- **「Dexieより総合的に優れている」→ 言い過ぎ**（実測していないメモリ/性能特性の懸念が残るため）

「10万件規模でのメモリ使用量は未計測」という限界を両方書いておくのが誠実だと思います。実際に懸念を解消したいなら、DevToolsのMemoryタブで10万件podを開いた状態のヒープサイズを一度計測しておくと、この結論に自信を持てるはずです。

## Dexieが10万件ソート問題を根本的に回避できる理由

DexieはIndexedDBのネイティブindexを直接使います。IndexedDBのindexは内部的に**B-treeとしてソート順を常時維持**しているため、`.offset(skip).limit(limit)` はカーソルを`skip`件分進めて`limit`件読むだけで済みます。計算量は **O(skip + limit)** であり、Mの全件を毎回ソートし直す必要がありません。

これに対してSignalDBの `Cursor.getItems()` は：
```
フィルタ(全件 or index絞り込み) → ①ソート(M件) → ②skip → ③limit
```
という順序で、**①のソートが毎回M件全体に対して走ります**。indexを張ってもフィルタ（O(N)→O(M)）は速くなりますが、ソート済みのindexという概念自体が無いため、ソートコストはM件分そのまま残ります。これはDeepWikiの回答が明言している通り、SignalDB側の設計上の限界であり、アプリ側で回避しようがありません。

## つまり構造的な違い

| | SignalDB | Dexie（indexが正しく設計できれば） |
|---|---|---|
| ソート済み状態の保持 | 無い（毎回JSでソート） | Bツリーindexが常に保持 |
| クエリ再評価コスト | O(M log M)（Mはフィルタ後件数） | O(skip + limit) |
| 更新1件によるrequeryコスト | 毎回M件の再ソート | カーソル操作のみ、Mに依存しない |

「更新頻度が高い場合、これは無視できないコスト」とDeepWikiが述べているのは、まさにこの毎回の再ソートのことです。Dexieのindexベースのカーソルなら、この再ソートコスト自体が発生しません。

## ただし以前指摘した制約とのトレードオフ

ここで以前の会話の論点が戻ってきます。`{ pin: -1, position: -1, id: 1 }` という**混在方向**の複合ソートは、単一のcompound indexでは表現できません。Dexieでこの恩恵（O(skip+limit)）を得るには、例えば：

- `pin` は二値なので、pinnedとunpinnedを**別々のクエリ**に分割する
- それぞれ `position` 単一方向のindexに対して `.reverse()` でカーソル走査する
- `id` の昇順tie-break（position完全一致時のみ関係）は妥協するか、`[position+id]` の複合indexにして両方降順で近似する

という設計変更が必要です。つまり「Dexieならこの問題が自動的に解決する」のではなく、**データモデルとクエリの組み方を変える手間を払って初めて**、SignalDBには無い「ソート済みindexによるO(skip+limit)」という恩恵を得られる、という関係です。

## 結論

- 「アプリ側で制御する必要がある」という点は、**SignalDBを使い続ける限り**その通りです（DeepWikiが挙げた「ソート済みキャッシュ」「クエリ単位のメモ化」「ページ単位でderived storeを持つ」など、いずれもアプリ側の追加実装が必要）
- しかし「Dexieでも変わらないか」というと、**変わります**。Dexieはこの種のページングクエリを本来得意とする設計（ネイティブB-treeカーソル）であり、正しくindexを設計できれば「毎回M件を再ソートする」というコスト自体が発生しません
- 代償は、混在方向ソートを実現するためのクエリ分割・データモデル調整という実装コストです

つまり、**「実装のシンプルさ」ではSignalDBが勝ち、「大規模データでのページングクエリの理論的効率」ではDexieが勝つ**、という以前からの評価軸がここでも一貫しています。10万件規模で実際にパフォーマンス問題が顕在化した場合の対処法としては、SignalDB側でアプリコードを複雑にするより、Dexie側でindex設計を工夫する方が筋が良い可能性がある、というのが正直な評価です。
